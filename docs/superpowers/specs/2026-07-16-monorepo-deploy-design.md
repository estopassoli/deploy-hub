# Design: Monorepo & package-manager-aware deploys

**Date:** 2026-07-16
**Status:** Implemented
**Area:** `backend/src/deploy`, `backend/src/apps`, `backend/prisma`, frontend `src/pages/Deploy.tsx` + config modal

## Problem

DeployHub assumes every project is a single-app **npm** repo. Two concrete failures:

1. **Auto-heal kills pnpm deploys.** After a successful pnpm install + Prisma migrate, the
   panel runs an internal "installing missing dev dependencies" step that executes
   `npm install --save-dev @types/node --force` inside a pnpm workspace. This mixes npm into a
   pnpm repo and, in the reported case, npm itself crashed
   (`Cannot read properties of null (reading 'matches')`), failing the deploy. The "missing"
   check is also naive: it looks only in `<release>/node_modules/@types/node`, but pnpm hoists
   `@types/node` to the workspace-root `node_modules` (exposed from `node_modules/.pnpm` via
   symlink), so it produces a false positive and fires the npm install for nothing.

2. **No package-manager or workspace awareness.** Install/build/start default commands are
   hardcoded to npm and to the repo root. There is no way to target a workspace package
   (`apps/backend`) or a specific package manager (pnpm/yarn), and build CLIs (nest/next/tsc/prisma)
   that live in `devDependencies` get skipped when `NODE_ENV=production`.

## Goals / Acceptance criteria

1. Deploying a **pnpm + Turbo** monorepo (install at root, build/start filtered by app) succeeds
   with **no `npm` invocation generated by the panel**.
2. With `NODE_ENV=production`, devDependency build CLIs (nest/next/tsc/prisma) are available
   during the build.
3. The "missing dev dependencies" routine never runs `npm` on a pnpm/yarn project and never brings
   down a deploy.
4. App-type detection reads the **target app's** `package.json` in monorepo mode.
5. A single-app npm deploy keeps working exactly as before (no regression).

## Non-goals (this iteration)

- **Nx first-class support.** Turbo + pnpm/yarn/npm workspaces are covered. Nx repos still work by
  the user typing an `nx ...` custom build/start command; we do not auto-detect `nx.json` yet.
- **`pnpm prune --prod` after build.** Deliberately omitted — pruning can strip runtime deps that
  `next start` needs. Left as a future opt-in.
- **Bun.** Not a supported package manager target (npm/pnpm/yarn only).

## Decisions (locked)

| # | Decision | Choice |
|---|----------|--------|
| A | Auto-heal fate | **Remove entirely.** Item B guarantees build devDeps are present. |
| B | Build/start command generation | **Turbo-aware auto.** `turbo.json` present → `turbo run build --filter=<pkg>`; else `<pm> --filter <pkg> run build`. |
| C | Tooling breadth | **Turbo + pnpm/yarn/npm.** Nx is manual-command-only. |
| D | `.env` location in monorepo | **Both** repo root and target app dir. |

### Accepted tradeoffs

- Removing auto-heal means projects that **never declared** `typescript` / `@types/node` /
  `@nestjs/cli` in their `devDependencies` (and relied on the panel to inject them) will now fail
  to build until they declare them. This is intended: item B installs *declared* devDeps correctly;
  the panel stops silently mutating package.json/lockfiles.
- In **monorepo mode**, the app type **detected from the app's package.json** overrides the
  dropdown selection. In **single-app mode** the dropdown stays authoritative (regression safety).

## Architecture

### New module: `backend/src/deploy/package-manager.ts` (pure, unit-tested)

Command generation is extracted into pure functions so it can be tested without spawning processes
(`deploy.service.ts` is already 770 lines and shells out for everything).

```ts
type PmName = 'npm' | 'pnpm' | 'yarn';
interface PmInfo { name: PmName; version?: string; berry: boolean; viaCorepack: boolean; }

detectPackageManager(rootDir): PmInfo
  // 1. package.json "packageManager" field (authoritative; sets viaCorepack, version, berry from major)
  // 2. lockfile at root: pnpm-lock.yaml -> pnpm | yarn.lock -> yarn | package-lock.json -> npm
  // 3. default npm
  // berry: yarn with major >= 2, OR presence of .yarnrc.yml

installCmd(pm, { includeDev, frozen }): string
  // pnpm  -> pnpm install [--frozen-lockfile] --prod=false
  // npm   -> npm ci --include=dev   (or: npm install --include=dev when not frozen)
  // yarn berry    -> yarn install --immutable
  // yarn classic  -> yarn install [--frozen-lockfile] --production=false

runScriptCmd(pm, { pkg?, script }): string
  // monorepo (pkg set):
  //   pnpm -> pnpm --filter <pkg> run <script>
  //   yarn -> yarn workspace <pkg> run <script>
  //   npm  -> npm run <script> --workspace <pkg>
  // single-app: pnpm|yarn|npm run <script>

execCmd(pm, { pkg?, argv }): string
  // runs a binary in the (package) context. Exact strings (locked by unit tests):
  //   pnpm  monorepo -> pnpm --filter <pkg> exec <argv...>      single -> pnpm exec <argv...>
  //   yarn  monorepo -> yarn workspace <pkg> exec <argv...>     single -> yarn exec <argv...>  (classic + berry, same form)
  //   npm   monorepo -> npm exec --workspace <pkg> -- <argv...>  single -> npx <argv...>
  // NOTE: pnpm/yarn workspace-scoped exec run with cwd = the package dir.

turboBuildCmd(pm, pkg): string
  // execCmd(pm, { argv: ['turbo','run','build','--filter='+pkg] })  e.g. `pnpm exec turbo run build --filter=@blurp/backend`

detectAppType(appWorkDir): 'nextjs' | 'nestjs' | 'vitejs' | null
  // reads appWorkDir/package.json deps+devDeps:
  //   next -> nextjs | @nestjs/core -> nestjs | vite -> vitejs | else null
```

### Deploy pipeline changes (`backend/src/deploy/deploy.service.ts`)

Resolve once near the top of `executeDeploy`:

```
releaseDir   = <APPS_DIR>/<app>/releases/<ts>        (repo root; where git clones)
appDir       = app.appDir  (optional, e.g. "apps/backend")
appWorkDir   = appDir ? join(releaseDir, appDir) : releaseDir
pkg          = app.workspacePackage || (appDir ? read appWorkDir/package.json .name : undefined)
isMonorepo   = Boolean(appDir || app.workspacePackage)
pm           = detectPackageManager(releaseDir)
effectiveType = isMonorepo ? (detectAppType(appWorkDir) || app.type) : app.type
```

Pipeline steps:

1. **Clone** — unchanged.
2. **Write `.env`** — write to `releaseDir/.env` and, when `appWorkDir !== releaseDir`, also to
   `appWorkDir/.env`. Env vars continue to be exported into every step's process env (via
   `runCommand` `extraEnv`) and into the PM2 `env` block — that part already works and is kept.
3. **Corepack** — if the `packageManager` field is present, run `corepack enable` at `releaseDir`
   first, wrapped in try/catch → warn only (never fatal). Falls back to system pnpm/yarn.
4. **Install** — always at `releaseDir` (root). Custom `installCommand` wins verbatim; otherwise
   `installCmd(pm, { includeDev:true, frozen:true })` with the existing "frozen failed → retry
   non-frozen" fallback generalized per PM.
5. **Prisma** — detect schema at `appWorkDir/prisma/schema.prisma` OR `releaseDir/prisma/schema.prisma`.
   - generate default: `execCmd(pm, { pkg: isMonorepo?pkg:undefined, argv:['prisma','generate'] })`
   - migrate default (when no custom `migrateCommand`): `execCmd(pm, { pkg, argv:['prisma','migrate','deploy'] })`
   - custom `migrateCommand` still wins.
6. **~~Auto-heal~~** — **deleted** (both the nestjs and nextjs "missing dev dependencies" blocks).
7. **Build** — custom `buildCommand` wins (run at `releaseDir`). Default:
   - monorepo + `turbo.json` at root → `turboBuildCmd(pm, pkg)`
   - monorepo, no turbo → `runScriptCmd(pm, { pkg, script:'build' })`
   - single-app → today's behavior, PM-aware: `effectiveType==='nestjs'` → `execCmd(pm,{argv:['nest','build']})`,
     else `runScriptCmd(pm,{script:'build'})`.
   - cwd = `releaseDir` (filter/turbo commands need workspace-root context).
8. **Symlink `current`** — unchanged.
9. **Start / static:**
   - PM2 (`effectiveType` nestjs/nextjs): `generatePM2Config` gains `pm`, `pkg`, `isMonorepo`,
     `effectiveType`. Custom `startCommand` still parsed into script/args as today. Monorepo default
     uses `execCmd(pm,{pkg,argv:[...]})` which runs **in the package dir** with `PORT` injected:
     - nextjs → `<pm> --filter <pkg> exec next start --port <port>` (forces configured port)
     - nestjs → `<pm> --filter <pkg> run start` (or `start:prod` if that script exists)
     Single-app PM2 config unchanged (Next `node_modules/.bin/next start --port`, Nest `npm run start`).
     `NODE_ENV` default stays `production`; user env vars still override (merged after base env).
   - Vite static (`effectiveType==='vitejs'`): copy dist from `appWorkDir/dist` (not `releaseDir/dist`)
     when `appDir` is set.
10. **Nginx / SSL** — unchanged (proxy targets `app.port`, which the scoped start honors via PORT).

**Deployment mode is driven by `effectiveType`, not `app.type`.** Every branch that currently
switches on `app.type` in the deploy path — `generatePM2Config` `isSupported`, PM2-vs-static-copy,
and the proxy-vs-static nginx config selection — uses `effectiveType`. So a monorepo app whose
detected framework differs from the stored dropdown still deploys in the correct mode. In single-app
mode `effectiveType === app.type`, so behavior is identical to today.

### Data model (`backend/prisma/schema.prisma`)

Add to `model App`:
```prisma
appDir           String?   // monorepo target subdir, e.g. "apps/backend"
workspacePackage String?   // workspace package name, e.g. "@blurp/backend"
```
Add a Prisma migration. Package manager is detected per-deploy from the lockfile and **not**
persisted (no column needed).

### API / DTO

- `DeployDto` (`deploy.controller.ts`): add optional `appDir`, `workspacePackage` (`@IsOptional @IsString`).
- `CreateAppDto` / `UpdateAppDto` (`apps.controller.ts`): add both fields.
- `deploy.service.ts` `deploy()` persists `appDir`/`workspacePackage` on the app (like the command
  fields) and passes them to `executeDeploy`; `redeploy()` reads them from the app.
- `apps.service.ts` `create()`/`update()` accept and store both fields.

### Frontend

- `src/pages/Deploy.tsx`: new **"Monorepo (optional)"** section with two inputs — "App Directory"
  (placeholder `apps/backend`) and "Workspace package name" (placeholder `@blurp/backend`). Add to
  `formData`, `resetForm`, and the `api.deploy` payload. Helper text notes `.env` is written to both
  the repo root and the app directory.
- `src/components/dashboard/AppConfigModal.tsx`: same two fields for editing an existing app.
- `src/lib/api.ts`: extend the deploy payload type.
- `src/types/app.ts`: add `appDir?`, `workspacePackage?` to `App` / deploy config types.

## Testing

- **Unit (jest) for `package-manager.ts`** — the core of the change and fully pure:
  - `detectPackageManager`: packageManager-field wins; each lockfile; default npm; yarn berry via
    `.yarnrc.yml` / major version.
  - `installCmd`: pnpm/npm/yarn (classic+berry) × frozen/non-frozen × includeDev.
  - `runScriptCmd` / `execCmd`: single-app vs monorepo filter/workspace forms per PM.
  - `turboBuildCmd`: correct `--filter=` string per PM.
  - `detectAppType`: next / @nestjs/core / vite / null, reading the given dir.
- **Manual acceptance (documented in the plan):** deploy a pnpm+Turbo monorepo and assert the log
  contains no panel-generated `npm ...`, build CLIs resolve, and the app serves on its port; and a
  regression pass with a single-app npm project.

## Risks

- **Server must provide the package manager.** pnpm/yarn must be installed or reachable via
  Corepack. Mitigation: `corepack enable` when the `packageManager` field is set; warn (non-fatal)
  if Corepack is unavailable so the failure is diagnosable in the deploy log.
- **`workspacePackage` without `appDir`.** Filter-based build/start still work, but app-relative
  concerns (app-type detection, per-app `.env`, Next `.next` cwd, Vite dist path) fall back to root.
  Mitigation: treat App Directory as the recommended primary field; document it in the form.
- **Prisma monorepo generate scope.** `execCmd` runs prisma in the package dir via `--filter ... exec`,
  matching the user's known-good `pnpm --filter @blurp/backend exec prisma migrate deploy`.
